Overall Requirements\n1. Context Diagram\nAgriSustain is a digital e-commerce platform for agricultural products that directly connects farmers and cooperatives with consumers and B2B buyers. The system supports product search and trading, crop and shipment management, QR-based traceability, production pre-ordering, B2B off-take contracts, online payments, dispute resolution, and operational reporting.\nKey actors include Guests, Consumers, B2B Buyers, Farmers, and Administrators. The system also interfaces with the VietQR/PayOS payment gateway to generate payment codes and receive transaction results. The Context Diagram below illustrates the system boundaries and the primary data flows between AgriSustain and external actors.\n2. User Authentication\n1.1 User Register\n1.2 Sign In Screen\n1.3 Change Password\n1.3.1 Change Password\nThis screen allows an Authenticated User to change their account password. The user enters the current password, a new password, and confirms the new password. The system validates the current password and checks the new password against the password policy before updating the account. \n1.4 Reset Password\nThis screen allows Guest and registered users to recover access to their account when they forget their password. Users enter their registered email address, verify a one-time password (OTP) sent to that email, and create a new password. The system validates the OTP, checks that the new password satisfies the password policy, securely updates the password, and redirects the user to the Sign In screen after a successful reset.\n1.4 Logout\n2. MarketPlace\n2.1 Browse Marketplace \n2.1.1 Browse Marketplace \nThis screen allows Guest, Consumer, and Buyer B2B users to browse public agricultural products. Users can search for and filter products by name, category, supplier, region, season, or certification. \n2.2 View Product Detail \n2.1.1 View Product Detail \nThis screen allows Guest, Consumer, and Buyer B2B users to view detailed information about a publicly available product. The main information includes product description, price, available stock/batches, farm information, certificates, and eligible reviews. \n3. Farmer Sales\n3.1 Process Order\n3.1.1 Farmer Order Fulfillment Screen\nThis screen allows the Farmer to:\nView Order List: View all incoming and ongoing orders with product details, batch codes, delivery addresses, and carrier information.\nFilter by Status: Filter orders by fulfillment stages (All, Confirmed, Processing, Awaiting Shipper, In Transit, Delivered) with real-time counter badges.\nSearch Orders: Filter orders by order type (Standard, Pre-Order), date range, or keywords (Order ID, buyer name, batch code).\nConfirm Order: Verify batch inventory and accept confirmed orders to reserve stock and begin fulfillment.\nReject Order: Decline an order with a mandatory explanation if produce fails quality checks or due to adverse weather.\nConfirm Packaging: Mark items as packed and labeled with batch QR codes, notifying the carrier for pickup.\nHand Over Goods: Confirm handover of packages to the courier to initiate transit and delivery tracking.\n3.2   Information Farmer \n4. Background Job Inventory\n7.1 Expire Password Reset Tokens (JOB-01) \nTrigger: Scheduled — Runs every 15 minutes. \nPurpose: Invalidate expired password-reset OTPs and security tokens across the platform to mitigate brute-force and token replay vulnerabilities.  \nProcessing steps:\nQuery active token records / OTP verification caches where expiration timestamp < CurrentTimestamp().\nTransition matching tokens/OTPs to Expired or remove unconsumed transient session tokens.\nLog the total number of invalidated tokens per execution cycle.\nFailure behavior:\n7.2 Auto-Cancel Unpaid Retail Orders (JOB-02) \nTrigger: Scheduled — Runs every 30 minutes. \nPurpose: Automatically cancel retail orders that remain unpaid beyond the configured payment time limit (e.g., 15–30 minutes) and restore reserved batch inventory to ensure active stock availability.\nProcessing steps:\nScan the Orders table for records where OrderType = 'Retail', OrderStatus = 'PendingPayment', and elapsed time exceeds the allowed checkout window.\nFor each identified order within an atomic transaction:\nUpdate OrderStatus to 'Cancelled'.\nRead ordered items from OrderItems and restore QuantityAvailable back into the respective ProductBatches.\nLog transaction detail in FinancialTransactions or audit history.\nEnqueue a notification to Notifications informing the Consumer of order expiration.\nCommit the transaction and log the count of cancelled orders and restocked quantities.\nFailure behavior:\n7.3 Reconcile Payment Status (JOB-03)  \nTrigger: Scheduled — Runs every 15 minutes. \nPurpose: Re-check and reconcile pending VietQR / PayOS payment transactions when inbound payment webhooks are delayed, dropped, or network-interrupted. \nProcessing steps:\nQuery Orders and FinancialTransactions where PaymentMethod IN ('VietQR', 'PayOS'), OrderStatus = 'PendingPayment', and creation time is between 5 and 60 minutes ago.\nCall the VietQR/PayOS query transaction status API using GatewayTransactionRef or Order Code.\nIf payment gateway returns PAID:\nUpdate transaction status to Success.\nUpdate Orders.OrderStatus to 'Paid'.\nDispatch an order payment confirmation alert to the Consumer and Farmer.\nIf payment gateway returns FAILED or EXPIRED:\nMark transaction as Failed.\nTrigger cancellation and inventory release logic.\nFailure behavior:\n7.4 Pre-Order Campaign Status Update (JOB-04)  \nTrigger: Scheduled — Runs every hour. \nPurpose: Automatically activate, close, or mark agricultural pre-order campaigns as completed based on configured start times, end times, target capacity limits, and campaign rules.  \nProcessing steps:\nQuery pre-order campaign entities and associated CropSeasons:\nActivate campaigns scheduled to start (StartTime <= CurrentTimestamp()) whose status is Scheduled.\nClose campaigns where EndTime <= CurrentTimestamp() or reserved volume reaches maximum campaign capacity.\nMark campaigns as completed once harvest fulfillment commences or status updates to Harvested.\nUpdate campaign status flags and restrict public pre-order cart submissions for closed/completed campaigns.\nNotify relevant Farmers regarding campaign status changes and final committed quantities.\nFailure behavior:\n7.5 Contract Milestone Reminder (JOB-05) \nTrigger: Scheduled — Runs daily at 8:00 AM.  \nPurpose: Notify B2B Buyers and Farmers about upcoming, due, or overdue B2B offtake contract milestones (e.g., scheduled harvest inspections, consignment dispatch dates, payment tranches).  \nProcessing steps:\nQuery OfftakeContracts with status 'Active' and retrieve milestone schedules matching notification thresholds (e.g., 3 days before milestone, day of milestone, or overdue).\nCompose contextual alerts outlining milestone title, contract code, due date, and expected obligations.\nInsert dispatched records into Notifications for both Buyer and Farmer accounts, and trigger external email notifications where configured.\nFailure behavior:\n7.6 Clean Up Old Notifications and Activity Logs (JOB-06) \nTrigger: Scheduled — Runs daily at 8:00 AM.  \nPurpose: Alert B2B Buyers prior to membership subscription expiration (e.g., 7 days and 1 day prior) and automatically update expired subscription statuses upon term completion. \nProcessing steps:\nIdentify records in BuyerSubscriptions where Status = 'Active' and EndDate <= CurrentDate() + 7 days.\nFor subscriptions nearing expiry: Dispatch renewal reminder alerts to the Buyer's account and email.\nFor subscriptions where EndDate < CurrentDate():\nIf AutoRenew = false: Update Status to 'Expired' and downgrade account tier entitlements (e.g., restricting access to MarketReports).\nIf AutoRenew = true: Enqueue recurring payment processing; if recurring charge fails, flag status as Expired.\nFailure behavior:\n7.7 Certificate Expiry Monitoring (JOB-07)  \nTrigger: Scheduled — Runs daily at 8:00 AM.   \nPurpose: Identify quality and safety certificates (VietGAP, GlobalGAP, Organic) nearing expiry (30 days prior) or already expired, and notify Farmers and Administrators while demoting unverified product badges.  \nProcessing steps:\nScan Certifications where VerificationStatus = 'Verified'.\nFor certificates where ExpiryDate <= CurrentDate() + 30 days and ExpiryDate >= CurrentDate(): Dispatch upcoming expiration reminders to the Farmer.\nFor certificates where ExpiryDate < CurrentDate():\nTransition certificate VerificationStatus to 'Expired'.\nIdentify products linked to the owner's FarmerID and unpublish/suppress verified certification badges on the Marketplace.\nNotify the Farmer and platform Administrator regarding certification deactivation.\nFailure behavior:\n7.8 Pending KYC Review Reminder (JOB-08) \nTrigger: Scheduled — Runs daily at 8:00 AM.   \nPurpose: Consolidate and notify platform Administrators of all Consumer, Farmer, or Buyer accounts currently pending legal/KYC document approval.  \nProcessing steps:\nQuery Accounts joined with Buyers and Farmers where Status = 'Pending' and KYC verification documents have been submitted.\nCount pending items by role and duration in queue (> 24 hours, > 48 hours).\nDispatch high-priority summary notifications and internal emails to platform Administrators with a direct navigation link to the KYC Application Review workspace.\nFailure behavior:\n7.9 Notification Delivery Retry (JOB-09) \nTrigger: Scheduled — Runs every 15 minutes.   \nPurpose: Resend failed in-app, system, or email notifications (e.g., Google Gmail API outages or network glitches) to guarantee message delivery. \nProcessing steps:\nQuery Notifications and email dispatch queues where DeliveryStatus = 'Failed' and RetryCount < 3.\nAttempt re-dispatching messages via the respective delivery channel (e.g., Google Gmail API for external alerts).\nOn success: Update status to 'Sent', record dispatch timestamp, and reset error code.\nOn failure: Increment RetryCount by 1. If RetryCount >= 3, mark status as 'PermanentFailure' and write to system error logs.\nFailure behavior:\n7.10 Archive Old Audit and Activity Logs (JOB-10) \nTrigger: Scheduled — Runs monthly on the 1st at 2:00 AM. \nPurpose: Archive or clean up historical system audit records, activity logs, and read notifications according to the platform’s data-retention policy (e.g., records older than 180 days) to optimize operational database indexing and query performance. \nProcessing steps:\nLoad configured retention cutoff threshold (e.g., CurrentDate() - 180 days).\nExport historical activity logs and read Notifications (IsRead = true) older than the cutoff threshold to compressed cold storage or dedicated archival tables.\nDelete archived records in controlled batches (e.g., 5,000 rows per batch) to prevent table locks and minimize CPU load.\nRecord the final count of archived entries in system maintenance telemetry.\nFailure behavior:\n8.
